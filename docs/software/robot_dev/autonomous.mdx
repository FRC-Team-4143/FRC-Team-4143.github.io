# Autonomous
Autonomous programming is a critical aspect of FRC robots, as it covers the first 15 seconds of the match where the robot operates without human intervention. During this period,
the robot must perform a series of pre-programmed actions to score points, navigate the field, and interact with game pieces. Effective autonomous routines can provide a significant
advantage in matches, as they allow the robot to maximize the points scored during this crucial phase where activity scores are higher.

This page documents how our autonomous stack works using MWLib and the mainbot code. The examples below are pulled directly from the 2026 robot code.

---

## Core Concepts

Our autonomous flow is split into three layers:

- **Auto routines** (`com.marswars.auto.Auto`): A command-based sequence (extends `SequentialCommandGroup`) that can run any robot commands (drive, shooter, intake, LEDs, etc.) and optionally load Choreo trajectories.
- **Auto manager** (`com.marswars.auto.AutoManager`): Handles the SendableChooser, displays the selected path, and returns the selected auto in `autonomousInit()`.
- **Drive integration** (`SwerveSubsystem`): Executes Choreo trajectories, exposes helpers like `setDesiredChoreoTrajectoryCommand`, and provides event triggers.

### Auto Lifecycle in Mainbot

The robot initializes autos once, registers them, and schedules the selected auto in `autonomousInit()`.

:::warning
Autos must be registered with `AutoManager` to appear in the chooser. If you don’t register them in `Robot.java`, they won’t show up on the dashboard.
:::

```java
// Robot.java
AutoManager.getInstance()
	.registerAutos(
		new Left_Start_Neutral_Outpost_Climb(),
		new Left_Start_With_Events());

@Override
public void autonomousInit() {
    Auto selected_auto = AutoManager.getInstance().getSelectedAuto();
    CommandScheduler.getInstance().schedule(selected_auto);
}
```

## Building an Auto Routine

Every auto extends `Auto` and follows the same pattern. Here’s a beginner-friendly breakdown of the flow:

1. **Decide what the robot should do (drive + actions)**
	- An auto can run any command: drive paths, spin up a shooter, run intake, set LEDs, or set subsystem state machines.
	- Think of it as a normal `SequentialCommandGroup` with autonomous-specific helpers.

2. **Pick your path files in Choreo (only if you want path following)**
	- Decide which trajectories you want the robot to drive in order.
	- Make sure those paths exist in the generated `ChoreoTraj` record.

3. **Load the trajectories at the top of the constructor**
	- Call `loadTrajectory(name)` for each path in the order you plan to run them.
	- This also caches poses for field display, so it must happen first.

4. **Tell the swerve subsystem which path to drive**
	- Use `setDesiredChoreoTrajectoryCommand(getTrajectory(name))` before starting each segment.

5. **Start the drive state that actually follows the path**
	- Switch to `CHOREO_PATH` (or `CHOREO_PATH_ROTATION_LOCK` if you need fixed heading).
	- End that command when `isAtChoreoSetpoint()` is true.

6. **Add any extra actions between or during paths**
	- Examples: shooting, intaking, waiting, or triggering events.
	- These are normal commands added to the sequence.

7. **Repeat for each additional path segment**
	- Set the next trajectory, switch the state, then wait for completion.

:::note
Choreo is just one tool in your auto. You can run any WPILib command and set any subsystem state machine state alongside (or instead of) trajectories.
:::

### Basic Path-Following Example

```java
public class TestAuto extends Auto {
    public TestAuto() {
	// 1) Load trajectories in the order they will run
	loadTrajectory(ChoreoTraj.LeftStartNeutralOutpost.name());
	loadTrajectory(ChoreoTraj.OutpostClimb.name());

	// 2) Build the command sequence
	addCommands(
		// Set the initial trajectory
		SwerveSubsystem.getInstance()
			.setDesiredChoreoTrajectoryCommand(
				getTrajectory(ChoreoTraj.LeftStartNeutralOutpost.name())),

		// Start following the trajectory
		Commands.startEnd(
				() -> SwerveSubsystem.getInstance()
					.setWantedState(SwerveStates.CHOREO_PATH),
				() -> SwerveSubsystem.getInstance()
					.setWantedState(SwerveStates.FIELD_CENTRIC))
			.until(SwerveSubsystem.getInstance()::isAtChoreoSetpoint),

		// Move to the climb position
		SwerveSubsystem.getInstance()
			.setDesiredChoreoTrajectoryCommand(
				getTrajectory(ChoreoTraj.OutpostClimb.name())),
		Commands.startEnd(
				() -> SwerveSubsystem.getInstance()
					.setWantedState(SwerveStates.CHOREO_PATH),
				() -> SwerveSubsystem.getInstance()
					.setWantedState(SwerveStates.FIELD_CENTRIC))
			.until(SwerveSubsystem.getInstance()::isAtChoreoSetpoint));
    }
}
```

### What the `Auto` Base Class Provides

MWLib’s `Auto` class handles Choreo trajectory loading and basic helpers:

- `loadTrajectory(name)`: Loads a Choreo trajectory and stores its poses for path display.
- `getTrajectory(name)`: Returns the typed `Trajectory<SwerveSample>` for swerve following.
- `getStartPose()`: First pose of the first trajectory (used for sim resets).
- `getPath(alliance)`: Poses for display in `Field2d`, auto-flipped for red alliance.

## Choreo Event Markers (Time and Pose)

The swerve subsystem integrates MWLib’s `ChoreoEventTracker`, which provides triggers for event markers defined in Choreo. There are two kinds of triggers:

- **Time Trigger**: Fires once the event timestamp has passed.
- **Pose Trigger**: Fires when the robot is within tolerances of the event’s pose (ignores time).

:::note
Triggers are meant for actions that happen while the robot is still following a path (like spinning up the shooter during a drive). If you want to run something after the path is finished, you can just wait for `isAtChoreoSetpoint()` and then schedule the next command in the sequence.
:::

### Example: Binding Actions to Events

In a real auto, you can bind subsystem states to event markers that happen during path following. **Event triggers should be registered before `addCommands()`**:

```java
public class Left_Start_Neutral_Outpost_Climb extends Auto {
    public Left_Start_Neutral_Outpost_Climb() {
        // Register trajectories first
        loadTrajectory(ChoreoTraj.LeftStartNeutralOutpost.name());
        loadTrajectory(ChoreoTraj.OutpostClimb.name());

        // Bind event triggers BEFORE addCommands
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Intake Out")
            .onTrue(
                Commands.runOnce(
                    () -> IntakeSubsystem.getInstance()
                        .setWantedState(IntakeStates.INTAKE)));
        
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Intake In")
            .onTrue(
                Commands.runOnce(
                    () -> IntakeSubsystem.getInstance()
                        .setWantedState(IntakeStates.STORE)));
        
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Shooting")
            .onTrue(
                Commands.runOnce(
                    () -> {
                        ShooterSubsystem.getInstance()
                            .setWantedState(ShooterStates.SHOOT);
                        SwerveSubsystem.getInstance()
                            .setWantedState(SwerveStates.CHOREO_PATH_ROTATION_LOCK);
                    }));
        
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Stop Shooting")
            .onTrue(
                Commands.runOnce(
                    () -> {
                        ShooterSubsystem.getInstance()
                            .setWantedState(ShooterStates.TRACKING);
                        SwerveSubsystem.getInstance()
                            .setWantedState(SwerveStates.CHOREO_PATH);
                    }));

        // Build the command sequence
        addCommands(
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setTarget(FieldTargets.Shooter.HUB)),
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setWantedState(ShooterStates.TRACKING)),
            
            // First path
            SwerveSubsystem.getInstance()
                .setDesiredChoreoTrajectoryCommand(
                    getTrajectory(ChoreoTraj.LeftStartNeutralOutpost.name())),
            Commands.startEnd(
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH),
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.FIELD_CENTRIC))
                .until(SwerveSubsystem.getInstance()::isAtChoreoSetpoint),
            
            new WaitCommand(3),  // Wait for shooting
            
            // Second path
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setWantedState(ShooterStates.SHOOT)),
            SwerveSubsystem.getInstance()
                .setDesiredChoreoTrajectoryCommand(
                    getTrajectory(ChoreoTraj.OutpostClimb.name())),
            Commands.startEnd(
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH_ROTATION_LOCK),
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.FIELD_CENTRIC))
                .until(SwerveSubsystem.getInstance()::isAtChoreoSetpoint));
    }
}
```

**Key patterns shown here:**

- Event triggers are registered **before** `addCommands()` so they're active during path following.
- Use `CHOREO_PATH_ROTATION_LOCK` when you need to maintain a specific heading (e.g., shooting while moving).
- Switch between subsystem states using event markers during the path.
- After each path finishes, you can run additional commands (waiting, shooting, etc.).

### Pose-based Triggers

You can also trigger on proximity to an event pose instead of time:

```java
SwerveSubsystem.getInstance()
    .getChoreoEventPoseTrigger(
        "Shooting",
        Units.inchesToMeters(6),     // Position tolerance
        Units.degreesToRadians(5))   // Rotation tolerance
    .onTrue(Commands.print("At shooting pose!"));
```

## Building Complex Cycling Autos

For competitive autos with multiple scoring cycles, you'll typically run multiple trajectories in sequence, each with its own event markers. Here's a simplified version of a 3-cycle auto:

```java
public class Neutral_Cycles extends Auto {
    public Neutral_Cycles() {
        // Load all trajectories in sequence
        loadTrajectory(ChoreoTraj.CycleNeutralFirst.name());
        loadTrajectory(ChoreoTraj.CycleNeutralThird.name());
        loadTrajectory(ChoreoTraj.OutpostClimbNeutral.name());

        // Bind event triggers
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Intake Out")
            .onTrue(Commands.runOnce(
                () -> IntakeSubsystem.getInstance()
                    .setWantedState(IntakeStates.INTAKE)));
        
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Intake In")
            .onTrue(Commands.runOnce(
                () -> IntakeSubsystem.getInstance()
                    .setWantedState(IntakeStates.STORE)));
        
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Shooting")
            .onTrue(Commands.runOnce(
                () -> {
                    ShooterSubsystem.getInstance()
                        .setWantedState(ShooterStates.SHOOT);
                    SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH_ROTATION_LOCK);
                }));
        
        SwerveSubsystem.getInstance()
            .getChoreoEventTimeTrigger("Stop Shooting")
            .onTrue(Commands.runOnce(
                () -> {
                    ShooterSubsystem.getInstance()
                        .setWantedState(ShooterStates.TRACKING);
                    SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH);
                }));

        addCommands(
            // Initialize subsystems
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setTarget(FieldTargets.Shooter.HUB)),
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setWantedState(ShooterStates.TRACKING)),
            
            // Cycle 1: Pick up first batch of game pieces
            SwerveSubsystem.getInstance()
                .setDesiredChoreoTrajectoryCommand(
                    getTrajectory(ChoreoTraj.CycleNeutralFirst.name())),
            Commands.startEnd(
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH),
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.FIELD_CENTRIC))
                .until(
                    () -> SwerveSubsystem.getInstance().isAtChoreoSetpoint()
                        && SwerveSubsystem.getInstance().hasChoreoTimeElapsed(1)),
            
            // Shoot
            Commands.runOnce(
                () -> {
                    ShooterSubsystem.getInstance().setWantedState(ShooterStates.SHOOT);
                    SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.FIELD_CENTRIC_ROTATION_LOCK);
                }),
            new WaitCommand(3),
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setWantedState(ShooterStates.TRACKING)),
            
            // Cycle 2: Pick up more game pieces
            SwerveSubsystem.getInstance()
                .setDesiredChoreoTrajectoryCommand(
                    getTrajectory(ChoreoTraj.CycleNeutralThird.name())),
            Commands.startEnd(
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH),
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.FIELD_CENTRIC))
                .until(
                    () -> SwerveSubsystem.getInstance().isAtChoreoSetpoint()
                        && SwerveSubsystem.getInstance().hasChoreoTimeElapsed(1)),
            
            // Final climb position
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setWantedState(ShooterStates.SHOOT)),
            SwerveSubsystem.getInstance()
                .setDesiredChoreoTrajectoryCommand(
                    getTrajectory(ChoreoTraj.OutpostClimbNeutral.name())),
            Commands.startEnd(
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.CHOREO_PATH_ROTATION_LOCK),
                    () -> SwerveSubsystem.getInstance()
                        .setWantedState(SwerveStates.FIELD_CENTRIC))
                .until(
                    () -> SwerveSubsystem.getInstance().isAtChoreoSetpoint()
                        && SwerveSubsystem.getInstance().hasChoreoTimeElapsed(1)),
            Commands.runOnce(
                () -> ShooterSubsystem.getInstance()
                    .setWantedState(ShooterStates.TRACKING)));
    }
}
```

**Key techniques in this auto:**

- **Multiple trajectories**: Each cycle is a separate loaded trajectory.
- **Shared event triggers**: All trajectories can use the same event names (e.g., "Intake Out").
- **Time buffers**: Use `hasChoreoTimeElapsed()` to ensure the robot dwells at pickup points.
- **State coordination**: Switch between `CHOREO_PATH` and `CHOREO_PATH_ROTATION_LOCK` as needed.
- **Sequential shooting**: Wait commands between paths for shooting to complete.

## Event API Reference


These helpers live on `SwerveSubsystem`:

- `getChoreoEventTimeTrigger(String eventName)` → `Trigger`
- `getChoreoEventPoseTrigger(String eventName, double translationTol, double rotationTol)` → `Trigger`
- `hasChoreoEventBeenPassed(String eventName)` → `boolean`

### Advanced Pattern: Time-Based Path Completion

For smoother transitions between paths (especially when cycling game pieces), you can add a time buffer to `isAtChoreoSetpoint()`:

```java
Commands.startEnd(
        () -> SwerveSubsystem.getInstance()
            .setWantedState(SwerveStates.CHOREO_PATH),
        () -> SwerveSubsystem.getInstance()
            .setWantedState(SwerveStates.FIELD_CENTRIC))
    .until(
        () -> SwerveSubsystem.getInstance().isAtChoreoSetpoint()
            && SwerveSubsystem.getInstance().hasChoreoTimeElapsed(1));
```

This pattern waits until:
1. The robot reaches the trajectory setpoint, **and**
2. At least 1 additional second has elapsed

This is useful when you want to dwell at the end of a path (e.g., to finish intaking) before moving to the next action.

## Field Display and Alliance Flipping

`AutoManager` keeps a `SendableChooser` and a `Field2d` display on the dashboard. It also flips
trajectories for red alliance when building the display path. This is automatic as long as you load
trajectories using `loadTrajectory()` in your auto.

## Tips and Gotchas

### General Patterns

- **Load trajectories first**: Call `loadTrajectory()` in constructor before `addCommands()`. This pulls in poses and events.
- **Event triggers before commands**: Register all `getChoreoEventTimeTrigger()` and `getChoreoEventPoseTrigger()` bindings **before** calling `addCommands()`.
- **Set the drive state**: The robot must be in `CHOREO_PATH` (or `CHOREO_PATH_ROTATION_LOCK`) to follow the trajectory.
- **End condition**: `isAtChoreoSetpoint()` is the standard way to wait for path completion.

### Swerve Drive States

- **`CHOREO_PATH`**: Follows both translation and rotation from the trajectory.
- **`CHOREO_PATH_ROTATION_LOCK`**: Follows translation but locks rotation (useful when shooting on the move).
- **`FIELD_CENTRIC`**: Normal driver control (used as end state after path following).
- **`FIELD_CENTRIC_ROTATION_LOCK`**: Field-centric but maintains heading (useful for stationary shooting).

### Time Buffers

Use `hasChoreoTimeElapsed(seconds)` in your `.until()` condition when you want to dwell at a position:

```java
.until(() -> 
    SwerveSubsystem.getInstance().isAtChoreoSetpoint() 
    && SwerveSubsystem.getInstance().hasChoreoTimeElapsed(1))
```

This is especially useful at game piece pickup locations where you need to wait for the intake to complete.

### Alliance Flipping

The swerve subsystem uses `SwerveConstants.FLIP_TRAJECTORY_ON_RED` (set when operator perspective changes) to automatically flip trajectories. `AutoManager` also flips the display path, so you only need to plan for blue alliance in Choreo.

### Debugging Tips

- **Visualize in sim**: The `Field2d` display shows your loaded trajectory before the match starts.
- **Check event names**: Make sure event marker names in Choreo match exactly what you use in `getChoreoEventTimeTrigger()`.
- **Start simple**: Begin with a single trajectory before adding multiple paths and event markers.

If you need new trajectories, generate them in Choreo and make sure the generated `ChoreoTraj` record is updated before using them in autos.
